Sources : documentation Meta « Reels Publishing » (AAC 48 kHz maximum, pas d'edit list), lecture du fichier.
3. **Correctifs appliqués et mesurés** : `-ar 48000`, `-use_editlist 0`, balises BT.709 et conversion colorimétrique seule (mêmes dimensions). Résultat : audio 48 kHz, 0 edit list, `color_space=bt709`, loudness −14,0 LUFS (inchangée), crête −3,1 dBFS. Effet sur les couleurs : faible (erreur moyenne sur l'aplat orange 6,1 -> 4,0 ; erreur globale inchangée).

Une réponse du Worker non JSON ou un délai dépassé n'étaient pas distingués d'un échec franc ; un succès sur une seule plateforme sortait en code 0 sans signal.
5. `--demo --publier` était possible (données factices publiables si la garde était désactivée).
6. **La PR #33 est fusionnée dans `main`** (commit de fusion `d40c3c3`, VÉRIFIÉ par clone le 2026-11-07), alors que l'AVANCEMENT du 2026-11-06 la disait « non fusionnée ». L'effet réel (garde astuce) reste à vérifier au premier run : voix, Worker, YouTube, Instagram non vérifiés.

## 5. Protection contre les publications en double

Implémenté dans le générateur (VÉRIFIÉ par tests simulés) :
- délai dépassé, erreur réseau, réponse non JSON ou JSON non objet -> `incertain` : **aucun réessai**, sortie en échec avec le message « vérifie YouTube et Instagram AVANT de relancer » ;
- une seule plateforme confirmée -> `partiel` : avertissement `::warning::`, résumé dans `GITHUB_STEP_SUMMARY`, sortie 0 (une sortie en échec inviterait à relancer, donc à dupliquer) ;
- le Worker n'est appelé qu'**une fois** par exécution, et jamais si le contrôle refuse.

**Impossible dans le générateur seul** (limite structurelle, VÉRIFIÉE par lecture du workflow) : l'exécuteur GitHub n'a pas de stockage durable ; un lancement manuel « publier » du même créneau republie la même astuce ; une relance après un envoi incertain ne peut pas être empêchée. L'anti-doublon durable doit vivre dans le Worker + D1 (schéma candidat, section 6). Les API YouTube/Instagram ne permettent pas de comparer les octets d'une vidéo publiée : une vérification distante se limite aux métadonnées (identifiant, compte, marqueur de créneau en description/légende) et n'est pas implémentée.

## 6. Schéma D1 candidat

`video/ledger/0001_video_ledger.sql` : réservation unique par créneau (`AAAA-MM-JJ:matin|soir`), prise du créneau par comparaison de révision, une observation par plateforme, observations terminales immuables, pas de suppression, `reported_complete` seulement avec les deux plateformes confirmées, `needs_reconciliation` sans retour possible.

- Tests sous SQLite (17) : réservation unique, 20 prises simultanées -> 1 gagnant, verrou de révision, immuabilité, succès partiel jamais « complet ». VÉRIFIÉ sous SQLite.
- **NON VALIDÉ sur Cloudflare D1** : triggers, `RAISE(ABORT)` et `changes()` dans un trigger non exécutés sur D1 ; la concurrence réelle entre isolats de Workers n'est pas reproduite par des threads SQLite. À essayer sur une base D1 de test, créée par Émilien, avant toute base réelle. Aucune migration lancée.
- `reported_*` signifie « déclaré par le Worker », pas « prouvé à distance ».
- Contrainte de conception connue : les deux plateformes doivent enregistrer leur résultat l'une après l'autre (révision lue puis incrémentée) ; deux écritures simultanées font échouer la seconde, qui doit relire et recommencer.
